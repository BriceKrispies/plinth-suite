# Round 1 review, Reviewer B: skeptical technical audience

Reviewer: B (skeptical technical audience member). Work item WG-5518.
Scope: the mission brief (`00-mission.md`) and all six proposals, read in full.
Method: each proposal was read as an expert engineer who expects superficial complexity and "AI magic". Scores are 0 to 10 and each carries a one-line justification. Weaknesses cite sections or script timestamps. Quantities quoted from the proposals are labelled as the proposals label them (configured, target, or measured). No proposal was disqualified; see the disqualification note at the end of each section.

Weights (from the brief): depth 20, composability 20, agent 15, visual 15, credibility 10, narrative 10, feasibility 5, reliability 5.

## Proposal 01: Fathom (Systems Complexity)

File: `proposals/01-systems-complexity.md`

### Scores

| Criterion (weight) | Score | Justification |
|---|---|---|
| Depth (20%) | 9 | Typed relational IR with a unit algebra and type checker (P14, P15), tree CRDT with fractional indices and move ops (P2), three-way merge with named conflicts (P6), HLC op log, and an RLS rewrite before planning (D.4). This is the only proposal whose core claims are specific enough to be attacked by an expert. |
| Composability (20%) | 9 | One operation registry generates UI, HTTP, CLI and MCP (section A.2); the B.2 composition map shows panels, alerts, exports, lineage and permissions all referencing the same IR type. |
| Agent / MCP (15%) | 8 | Two-phase writes with a plan object, `stale_base` with a merge preview, `scope_exceeds_owner`, `query.explain` and structured errors with `did_you_mean` (D.3, D.8). Strong, but the error that the stage depends on is shaped to be recovered (see weakness 4). |
| Visual (15%) | 6 | The wall is tables, a bar chart, a line chart and a status line. The stated mandate (screens react, panels appear) is carried mostly by text chips and a toast. Functional, not spectacular. |
| Credibility (10%) | 8 | Section G.5 lists shallow features candidly (anomaly as MAD bands, embedding as a signed iframe, no PDF layout engine). Credibility is cut back by the planted attribution numbers (weakness 1). |
| Narrative (10%) | 7 | Clear arc: question, drill, conflict, boundary, refusal, kill. The 255-300 s block is dense and the finance-permission story is muddled (weakness 5). |
| Feasibility (5%) | 5 | Fifteen dependency-ordered steps (H.4) with the tree CRDT named as the gating risk. The stack is large, and H.6 concedes that the IR and CRDT could each fail the demo. |
| Reliability (5%) | 5 | Three of the on-stage moments depend on timing that cannot be cued (concurrent human and agent edit, kill during an in-flight commit), and the stack has roughly a dozen services. |

Disqualify: no. The fault is modelled but the modelling is declared (A, G.3), and the data is generated by a real simulator process.

### Strongest ideas
- One operation registry that generates every surface, with plan/apply and the authorization verdict stored inside the plan (A.2, D.8). An expert can check this claim by looking for a second write path.
- Replay that re-issues the same MCP calls, compares semantic response content, and stops on a checkpoint-hash mismatch (C.3). This is the most credible fallback in the set.
- The "kill -9 during an agent commit, audit chain still verifies" beat is a falsifiable property with a named test (claim 5, `kill-resume.spec.ts`).
- The `scope_exceeds_owner` refusal is enforced by policy evaluated per request, not by the agent's token (D.6). That answers the obvious "can the agent escalate" question.
- Section G.5 is an honest list of shallow features, which builds credibility with this audience.

### Weaknesses (most severe first)
1. **The "finding" is the planted fault, read back.** Section C at 120-165 s has the agent report "dock NE-2 contributes 91%", "Northline 88% of NE-2's excess" and "handoff rate 0.82 to 0.31". Section G.3 says "the scenario file fixes the throttle", and the figures are scenario-file values (Section "Word count and notes"). An expert sees an answer key. The beat needs a negative control (a second dock with comparable noise and no throttle) and a run in which attribution reports no single dominant cause.
2. **The concurrency beat cannot be cued.** At 210-255 s the presenter types a title while the agent's `spec.commit` lands on a sibling property of the same node. The CRDT merge is correct, but nothing in the script makes the two writes collide inside the same window. The on-stage "two named authors on one node" chip depends on wall-clock timing. The rehearsal (C.3) checks the replay, not this beat.
3. **The 270-300 s montage has four claims in thirty seconds.** A workflow hold, a replica kill, a retried commit with the same idempotency key, a browser reconnect, and an audit verify. Claim 5 proves the kill at a random point across twenty runs, but the stage needs the kill to land on an in-flight commit. That is luck unless the presenter forces it, and the proposal does not say how.
4. **The self-correction is pre-shaped.** At 255-270 s, `alert.create` fails with `unknown_field: for` and `did_you_mean: "hold"`, and the valid alternatives list contains the intended key. The error text in D.3 is structurally the same as the script's. The audience sees the recovery the error was designed to permit. The honest version would show a miss that the agent corrects from the list without the hint, or a miss that the agent does not correct.
5. **The permission story is hard to state.** At 255-270 s the approval grant "applies only to the board", yet the finance window "shows the board minus the NE-2 panel, because the grant on the drill-down was never made", and row predicates hide NE-2 customers. Section C does not say in one sentence what finance may see and why. A skeptic will ask which grant did what.
6. **The fallback writes an agent transcript that the agent did not produce.** Section C.3 says the replay client "writes them to the agent session transcript with the same formatting", so the agent pane shows calls that were replayed as if live. The terminal is not projected, but the presenter's own pane is the thing a reviewer asks to inspect. The brief asks for invisibility of the switch, not a forged transcript. Label replayed calls in the pane.
7. **The stack is heavy for a five-minute live run.** Keycloak, Redpanda, MinIO, Postgres, DuckDB, OTel and Jaeger, Mailpit, Caddy, Chromium, two `fathomd` replicas, the simulator, ingest, and a Playwright rehearsal. H.3 leaves Vega and React rendering on wall hardware "unmeasured". A failure in any one of these is a failure on stage.
8. **The visual mandate is thin.** No panel on stage is spatial, animated, or differentiated beyond a bar chart and a line chart. A reviewer will judge the wall against "visual spectacle" and find a dashboard.

### Required changes
- Add a negative control to the attribution beat: a non-causal dock with similar noise, and a seed in which the answer is "no single cause". Remove the scenario-file percentages from the on-screen claim.
- Specify a deterministic trigger for the concurrent-edit beat (for example, a stale base created by a scripted API write at a known point), or drop the chip from the stage.
- Split the 270-300 s montage. Keep the kill and the audit verify, and move the workflow hold and the reconnect to a supporting view.
- Show one miss-and-recover on the alert error without the `did_you_mean` hint, or state explicitly that the hint is the recovery path.
- Write one sentence of finance permissions on the script's finance window and make the grant-scope story match it.
- Label replayed calls in the agent pane, in the same way 04 and 06 label replay.
- Reduce the stage stack to the services the script touches, and record which services a stage run actually needs.

## Proposal 02: Tessera (Visual Spectacle)

File: `proposals/02-visual-spectacle.md`
Note: the product name "Tessera" is also used by proposals 04 and 06 (see the comparative section).

### Scores

| Criterion (weight) | Score | Justification |
|---|---|---|
| Depth (20%) | 8 | Typed registry, revision store with JSON-Patch deltas and base-rev checks, path-level three-way rebase (D.5), RLS as a compiler predicate plus Postgres RLS, and a hash-chained change log that includes refusals (P03, D.7). |
| Composability (20%) | 8 | The composition map (B.2) and the query-to-panel-to-parameter-to-query loop are real. The 45-row inventory is long, and several rows are asserted rather than shown (weakness 4). |
| Agent / MCP (15%) | 8 | Ghost-overlay preview with a commit card, a tool list filtered by scope, `AUTHZ_SCOPE` with a policy id, and a structured error shape. The approval refusal and the grant flow are specific. |
| Visual (15%) | 8 | The ghost overlay, the trace ribbon, the phone-width audience session flipping from 403 to the board, and an end-of-session replay counter give the most screen-level change of the six. |
| Credibility (10%) | 7 | Animation is tied to sequence numbers (section A, "Every animation ... is driven by a real change event"), which is the right rule. Credibility is reduced by design targets used as script timings and by a WebGL renderer for 180 events per second. |
| Narrative (10%) | 8 | Clear five-minute arc with a named strongest moment and a closing counter. The 250-280 s row is internally inconsistent (weakness 3). |
| Feasibility (5%) | 5 | Five image families and a dependency-ordered build (section H, steps 1-13). Replay and the driver depend on the whole stack being stable first. |
| Reliability (5%) | 5 | Choreography is built from targets (15 s, 40 s, under 2 s) that are not measured, and the fallback rule switches at row boundaries only. |

Disqualify: no. Replay is a real replay of audited revisions, and the fallback is a real MCP client. The replay limits are in weakness 2.

### Strongest ideas
- The rule that every animation is driven by a sequence-numbered event, not a timer (section A). This is the single best honesty rule in the set.
- The ghost-overlay preview with a dry-run digest and an expiry, shown on the wall before any commit (25-45 s). It makes "preview before write" visible to the room.
- The refusal as a red trace entry with the policy id, followed by the agent taking the alternative without being asked (240-270 s).
- The guard that refuses to run the driver against an unexpected workspace hash (G, "Where the fallback takes over"). This is the right failure rule.
- Presence showing the agent as a participant with a labelled cursor, which keeps the agent visible as a principal rather than as a hidden hand.

### Weaknesses (most severe first)
1. **The choreography is built on design targets.** The script uses "pending 00:42", "carrier latency rises within about 15 s (target)", "falls back over about 40 s (target)", and "under 2 s (design target)" for acknowledge. None is measured, and section F labels them as targets. A five-minute script with several unmeasured timings is not a script that can be promised.
2. **The replay is a patch replay, and its counter overstates it.** Section M06 "Re-applies stored patches to a blank workspace", so the 285-300 s moment replays stored revisions rather than re-issuing the agent's MCP calls. Deterministic patch replay proves little about composition. The counter reads "34 calls, 3 commits, 1 refused, 1 approval, checkpoints 3/3". A refused call is not a revision and cannot be re-verified by patch replay. Section C also says "Each row in the table is a checkpoint", and there are about ten rows, so "3/3" contradicts the design.
3. **The script contradicts itself at 250-280 s.** The text reads "Types, from the Phone window's incident card, nothing; instead types into the terminal". The row is hard to follow, and a reader cannot tell which device the presenter uses.
4. **The inventory says more than the stage shows.** Forty-five rows, 31 "demonstrated". Rows V01 (visual types), V02 (cross-filter), V03 (drill) and P10 (masking) are marked demonstrated, but the stage shows bar, line and table only, and masking is claimed with "***" in the table without a beat. A reviewer counts the rows and then checks the stage.
5. **The trust model is inconsistent.** At 45-70 s the human "clicks commit" on the agent's proposal. At 150-180 s the agent "auto-commits" an investigation dashboard under its own scope. An enterprise audience will ask why an agent may commit a dashboard at all, and the proposal's answer (additive and reversible) is stated but not shown.
6. **The stack list reads as breadth for its own sake.** uPlot, ECharts and a custom WebGL renderer for stream rendering at 180 events per second, plus Yjs for annotation text. Three charting stacks and a WebGL path at this rate invite the question "why?" and cost credibility.
7. **The fourth identity is a sign-in the proposal does not explain.** The audience phone session is a viewer with no investigation access. That is a useful boundary, but the script does not say which viewer it is or how the phone gets its session.
8. **The closing is strong but depends on the replay's scope.** "The platform reconstructs an agent-built investigation from its own audit log" (final 30 s) is the strongest moment, but it is only as strong as weakness 2 allows.

### Required changes
- Replace the replay with an MCP re-issue of the recorded calls, checked against response hashes, as 01 and 06 do. Keep the patch replay as a second, labelled view.
- Replace each design-target timing with a rehearsal-measured number, or remove the timing from the script.
- Correct the checkpoint count so that it matches the number of rows in the table.
- Mark each inventory row "demonstrated" only if the stage shows it. Move the rest to supporting.
- Pick one commit rule for agent dashboards and state it once: either the human commits all agent output, or the agent commits additive panels and the audit row says so.
- Drop the WebGL renderer from the stack unless a measured stream rate needs it.
- Rewrite the 250-280 s row so that it names one device and one action.

## Proposal 03: Parapet (Enterprise Platform)

File: `proposals/03-enterprise-platform.md`

### Scores

| Criterion (weight) | Score | Justification |
|---|---|---|
| Depth (20%) | 8 | Cedar decisions with explanations, RLS with predicates set per transaction, column masks compiled into the projection, deterministic anomaly explanation over real Postgres lock data (B.2 rows 10-12, 26; D.4, D.6). Real Postgres lock contention is a concrete, checkable data source. |
| Composability (20%) | 8 | The composition map (B.6) ties identity, policy, RLS, query, metric, alert, workflow and approval into one chain, and the command layer serves UI, API and MCP. Breadth is narrower than 01 or 06 (weakness 6). |
| Agent / MCP (15%) | 8 | Discovery is filtered by principal, `POLICY_DENIED` names the policy id without leaking values, `query.preview` runs as a principal, and the tape driver refuses to run on diverged state. |
| Visual (15%) | 6 | Mostly tables and time series, with a topology panel derived from lineage. The governance moments (masked email, refusal card, approval card) are legible but static. |
| Credibility (10%) | 8 | The fault is a real maintenance job taking `ACCESS EXCLUSIVE` on `payments.ledger`, and the explanation templates only computed facts (G.4). The "denied query appears on the Security board" beat is the kind of thing a security engineer checks. |
| Narrative (10%) | 7 | The governance arc (who can see, refusal, undo) is strong, but nine agent prompts in 300 s make the arc dense (weakness 2). |
| Feasibility (5%) | 5 | Cedar, Postgres RLS, Keycloak or Cognito, ECS, Aurora, SES, WAF, plus headless Chromium for PDF. Section G.1 names double enforcement drift as the highest-impact risk. |
| Reliability (5%) | 5 | The 170-200 s conflict depends on a race between a human retitle and an agent apply (weakness 1). |

Disqualify: no. The lock contention and the masks are real. The "no SCIM, no tenant admin" limits are stated (G.4), so the claim is bounded rather than fake.

### Strongest ideas
- A fault that is real Postgres lock contention from a maintenance job, not a number in a chart (section A, "Why this matters"). The audience can check `pg_locks` on the database.
- `query.preview` as another principal, returning `412 of 9,812` rows visible to finance. The row filter is visible as a count, not asserted.
- Approval as a `forbid` decision that names an approval route and is resolved only by a human principal (B.2 row 13, D.6). Governance is a property of the policy engine, not of the UI.
- The tape driver's preconditions, and the refusal `reset required: run parapet demo reset` (C.3, Refusal). A wrong screen is treated as worse than a pause, which is the right rule.
- Audit rows carry `source: "tape"`, so the switch is visible to anyone who inspects the log (C.3, Execution). This is honest by construction.

### Weaknesses (most severe first)
1. **The conflict beat is a race that the script does not control.** At 170-200 s the SRE retitles the lock panel while the presenter's agent applies with a stale `base_rev`. Nothing makes the human edit land between the agent's read and apply. And the outcome, in which the agent "keeps the human's title and adds its own suffix ... without confirmation", is a model decision, not a platform property. The platform only returned `CONFLICT_REV`. The closing line "no silent overwrite" credits the platform for the model's choice.
2. **Nine prompts with model latency inside them.** The script asks for seven or more MCP calls in the 45-95 s block alone, and about nine agent turns across 300 s. Section C.3 triggers the tape after 12 s of silence. On a live model, most turns will exceed that. The proposal does not budget model latency and does not state the expected takeover rate.
3. **Brice's permissions are inconsistent.** Section C.0 lists `brice` as "admin, delegator". The 255-285 s row says "brice has no hr.comp read grant", and the agent's ceiling is brice's rights. A skeptic asks why an admin cannot read HR compensation. The approval gate depends on `Group::security`, which the proposal never assigns to brice, yet brice approves the external notify.
4. **The maintenance job is a planted answer.** The 135-170 s row says the change log shows "a maintenance job `ops-maint` took `ACCESS EXCLUSIVE`". The change log is written by the platform, and a Postgres lock taken by an outside job would not appear there unless the job is a registered service actor. The proposal does not say how the platform learns of the lock. If the job is registered, the attribution is pre-wired. If not, the row is fiction.
5. **The fault is staged, and the presenter refers to it in relative terms.** The fault is injected about six minutes before the start, so the investigation runs on a fixed anomaly. That is acceptable only if the audience is not told the fault was staged. The script does not say whether it is.
6. **The visual impact is limited.** The wall is a timeseries, a stat, a table and one topology panel. The governance moments are cards and tables. Nothing is spatial or temporal beyond a line chart.
7. **Density over the five minutes.** Each prompt carries 4-7 calls and a plan/apply pair, and the 255-285 s block adds a denied query and an audit row. The proposal's own brief warns against long explanation. This script will need the presenter to narrate over several agent turns.
8. **"Enterprise platform" is partly a checklist.** No SCIM provisioning, no tenant administration UI, and "Multi-tenancy is ... fixtures" (G.4). An enterprise audience will notice these gaps, and the proposal lists them as shallow rather than fixing them.

### Required changes
- Replace the 170-200 s race with a deterministic stale base (for example, a scripted API write at a fixed point), and make the title merge an explicit, user-visible choice rather than a model's suffix.
- Give each agent turn a latency budget, and state the expected takeover rate from rehearsal. Cut prompts to at most five, or move two of them to the pre-recorded fallback.
- Fix brice's role and group memberships in one table, and make the approval chain match it.
- Specify how the maintenance job's lock becomes a change row, or remove the row and attribute the lock from `pg_locks` only.
- State on screen, or in the script's staging note, that the fault is staged, so the presenter's claim is accurate.
- Add one visual that is not a table or a line: a lock-wait graph by backend would serve.

## Proposal 04: Tessera (Emergent Composition)

File: `proposals/04-emergent-composition.md`

### Scores

| Criterion (weight) | Score | Justification |
|---|---|---|
| Depth (20%) | 7 | Typed query AST with predicate injection before compilation, path-level merge over a log, and the explicit statement that re-execution has no incremental maintenance (D.4, G.5). The depth is real, but the query path is the simpler of the six. |
| Composability (20%) | 9 | Fifteen generic verbs over typed kinds, audit as a source, rules as queries, backtests that use the same compiler, and `ui.present` as the only tool that changes a screen (D.7, B.6). The best case for "one grammar, many compositions" in the set. |
| Agent / MCP (15%) | 8 | `schema.describe` with verbs, examples and errors, `node.preview` with `preview_token`, `PREVIEW_STALE`, and progress and cancellation notifications. The agent-path evidence is deferred to rehearsal (weakness 4). |
| Visual (15%) | 7 | Bars, a heatmap with a red cell, a rule sparkline, a toast, a Phone window with a form and a timeline, and the Exec view filtering in place. Varied, though most panels are standard charts. |
| Credibility (10%) | 7 | Honest about re-execution cost and about the single-writer-like behaviour of path merges. Credibility is reduced by inflated counts (weakness 5). |
| Narrative (10%) | 6 | The close is an acknowledge form and a state change, which is ordinary write-back. The stated strongest moment does not carry the weight the script gives it (weakness 1). |
| Feasibility (5%) | 5 | Twelve components, with the DuckDB binding and the TypeScript stack named as critical. The build order is not given as a sequence of checks. |
| Reliability (5%) | 5 | The 170-200 s conflict is a wall-clock race, and the 225-250 s rule firing depends on a virtual clock running at 6x. |

Disqualify: no. The fallback is a real MCP client with checks on result hashes, and the live/replay tag is shown to the audience.

### Strongest ideas
- Fifteen generic verbs with a `schema.describe` that the agent must read first. The proposal argues for generality over per-kind tools and says the trade-off should be tested with a model (G.6). That is the honest framing.
- Audit as a source, so "who changed this" is an ordinary query (B.6, composition 3). This is a concrete reason the platform is inspectable with its own tools.
- A rule's backtest over 30 days using the same compiler (D.4, C.2 100-135 s). The alert is validated against history before it is committed.
- `ui.present` as the only tool that changes a screen without a change, and recorded in the audit log as `kind=present` (D.7). An auditor sees the screen change as an event.
- The live/replay tag in the trace panel (C.3). Disclosing the replay in a low-contrast tag is a trust move that a skeptic respects.

### Weaknesses (most severe first)
1. **The closing beat is ordinary CRUD.** The final 30 s (250-300 s) is an agent-built acknowledge form, a tap, and a state change to `acknowledged`. The proposal calls this "the strongest moment". An expert sees a form write-back, which every workflow tool has.
2. **The "why" beat returns an empty audit answer.** At 60-100 s `query.run` against `audit.changes` "returns no changes in the window, which the agent reports". Then the cause is stated in prose: "one carrier's median handoff time doubled". The composition shows an empty result, then asserts a cause. The brief asks that the evidence be on the screen, and here the evidence is a heatmap cell.
3. **The concurrency beat depends on a race.** At 170-200 s a drag on the Ops board and an agent resize of the same panel happen at the same moment. "The first to commit wins" is correct, but the stage does not cue the collision. A reviewer will see that the conflict is either lucky or staged.
4. **The agent-path evidence is deferred.** The proposal's central agent bet is that a model can compose from fifteen generic verbs with rich schemas. Section F claim 5 reports this as a measured quantity from rehearsal, and section H.3 offers no mitigation beyond "rehearsal". The demo's agent is the riskiest part of the design and the proposal has no fallback for the agent path itself.
5. **The counts inflate composability.** "47 capabilities, 27 demonstrated" counts visual types as separate items (bar, line, table, KPI, heatmap, each "demonstrated"), and "Demonstrated (branch and merge of one dashboard)" while branch merge is not in the script. The count is a rhetorical device, and an expert will discount it.
6. **The 225-250 s silence depends on a virtual clock.** The generator runs at 6x, so the three-minute hold is about 30 s of wall time. A stalled virtual clock produces 30 s of silence on the stage, and the presenter says "Nobody asked the agent". Section G.2 has no row for a stalled clock beyond "the presenter sees the virtual clock in the status bar".
7. **The cancellation path is under-specified.** Section C.3 says the live agent's step is "cancelled through MCP notifications/cancelled", and the driver resumes from the transcript. A cancelled in-flight commit has an unknown outcome to the driver. The proposal relies on idempotency keys, but it does not say how the driver decides whether the cancelled commit applied, beyond comparing digests.
8. **The name collides with two other proposals.** This is a presentation problem, not a design flaw, but a reviewer will confuse the three "Tessera" documents.

### Required changes
- Move the strongest moment earlier, and make the closing beat a result the audience could not have predicted from the platform's CRUD surface (for example, the agent's own rule firing into the acknowledge flow).
- Show the evidence for the "why" on screen, as a query result with the watermark, and remove the prose cause unless the query supports it.
- Replace the drag-versus-agent race with a deterministic stale base, as 03 and 06 should do.
- Add an agent-path fallback that a skeptic can inspect: publish the rehearsal pass rate per question, with the failing runs shown.
- Recount the inventory, counting each visual type as one row and removing branch merge from "demonstrated".
- Specify how the driver resolves a cancelled commit: a digest check against the recorded post-state and a rule for when to re-issue.
- Rename the product.

## Proposal 05: Lodestar (Live Operational Resilience)

File: `proposals/05-operational-resilience.md`

### Scores

| Criterion (weight) | Score | Justification |
|---|---|---|
| Depth (20%) | 8 | Entity store with `expected_version`, change log with RFC 6902 inverse patches, plan/apply with `E_PLAN_STALE`, and policy with deny-overrides (D.1-D.7). The query IR is smaller than 01's and states its limits (D.4). |
| Composability (20%) | 7 | Alerts, incidents, annotations, workflows and actions all reference the same entity graph (B.6). The breadth is narrower, and the stage uses mostly panels, alerts and one approval (weakness 5). |
| Agent / MCP (15%) | 7 | Twenty generic tools, resources for discovery, plan/apply, filtered tool lists (fault actions absent from the agent's `tools/list`), and progress notifications. The fault console sits outside the agent's grants, which is a good design. |
| Visual (15%) | 7 | Status grid, timeseries, log stream, table, annotations on the chart, and a toast. The fault propagation is visible on the board. Mostly standard panels. |
| Credibility (10%) | 9 | Real processes: a Node fleet with `prom-client`, real Postgres and Redis, k6 with a fixed arrival schedule, Toxiproxy toxics, and Docker restart. Claim 3 measures fault-to-screen latency and reports the distribution. This is the most credible fault in the set. |
| Narrative (10%) | 8 | A single incident story from fault to approval to recovery to masked question, with a clear last 30 s. The masked table is the strongest governance beat. |
| Feasibility (5%) | 5 | Seventeen local containers and an ECS and Toxiproxy adapter behind one `FleetAdapter`. Dependency order is clear (H.4). |
| Reliability (5%) | 4 | The fault-to-alert timing is a design target, and the 20-second fallback rule collides with the stage's own call budget (weakness 1). |

Disqualify: no. The fault is real and the measurement plan is honest. The "pause" difference across environments is documented (weakness 4).

### Strongest ideas
- A real fault. `docker pause` locally and a Toxiproxy timeout toxic on AWS, both with the same observable symptom, and both recorded by the action (E, "What differs"). The audience sees a service that is really down.
- Claim 3's measurement plan: `lodestar demo measure --runs 20` reports the distribution of fault-to-firing-to-SSE latency (F.3). It is labelled as "not yet measured" and the report is the only source of the figure.
- The fault console is a presenter-only control, outside the agent's grants and absent from its `tools/list`. The agent cannot cause the fault, so its diagnosis is not self-fulfilling.
- The masked customer table built by the agent, with the agent's principal unable to see unmasked emails and Ada able to. This makes row and column policy visible to the audience through a result they can read.
- Recovery is a first-class path: `resolved` after restart, measured by the same harness as the fault (claim 3).

### Weaknesses (most severe first)
1. **The live budget contradicts the fallback rule.** At 75-110 s the agent must make about eight calls (describe, query, alerts, logs query, lineage, plan, apply, screen show) in about 35 s, with progress lines. Section C.3's trigger fires after 12 s of silence while a call is expected. On a live model this will fire on most turns, so the "live" default is mostly replay. The proposal must budget model latency or state its expected takeover rate.
2. **Seventeen containers on the presenter's laptop.** `app-api`, `app-runner`, `postgres`, `victoriametrics`, `loki`, `redis`, six harbor services, `toxiproxy`, `k6`, `dex` and `caddy`, with a Docker socket for fault control. Section G.2 handles "laptop resource exhaustion" by refusing to reset during a fault, which does not protect a stage that is stalling mid-run.
3. **The alert timeline is written as if the target holds.** At 45-75 s the alert "goes pending, then firing after its for-duration (10 s)". The design target is "p95 at or below 20 s" from fault to firing with a 5 s scrape, and the figure is not measured. The script's visible result is stated as certain.
4. **"Pause" is a different fault on AWS.** Locally it is `docker pause`. On AWS it is a Toxiproxy timeout toxic, and the proposal says the two are "observably similar". The presenter's button says "Pause payments" in both environments. An expert will ask whether the alert measured on one holds on the other, and the proposal answers only that the action records which mechanism ran.
5. **The composition is narrower than the claim.** The stage uses panels, one alert, one incident, one annotation, one approval and one action, plus a plan/apply for a dashboard. Topology, scheduled export, forms and comments are supporting rows (B.3, B.4), and the stage does not use them. The proposal is credible about what it does and quieter about breadth.
6. **The strongest moment depends on coincidence.** At 270-300 s the agent builds a masked table "in under 15 s", and the orders health row "changes in the same frame". The presenter presses Inject and says "Watch the board, not me". Two independent events must align in one frame, and the script names no mechanism for aligning them.
7. **The agent never causes a fault, which is honest but halves the loop.** The agent investigates a fault the presenter injects. That is correct for the brief's credibility bar, but the audience sees a diagnosis without an action that changes the system, except for a restart that a human approves.

### Required changes
- Budget model latency per turn in the script, and state the takeover rate observed in rehearsal. If the rate is high, cut the number of agent calls per turn (fewer, larger plans), as 06 proposes.
- Reduce the local stack to the services the stage uses. Name the containers the stage needs and keep the rest in a separate profile.
- Show the alert's pending and firing times as measured values from the last rehearsal, not as script facts.
- Either make the AWS fault a true pause (for example, a container stop with a documented restart) or state on the stage that the mechanisms differ.
- Replace the "same frame" alignment with an explicit sequence: the table appears, then the fault is injected, or the reverse, whichever the measured timing supports.
- Consider one agent-caused action that is reversible and visible on the board, so the loop is closed by the agent.

### Strongest ideas
- Preview and commit as one code path, with the digest of the proposal checked against the commit (D.5, F.1). Most dashboard tools have two paths. An expert engineer will ask for exactly this test, and the proposal provides it.
- `IDEMPOTENCY_KEY_REUSED`, returned with the original changeset id, so an agent cannot silently overwrite a prior decision (D.5, Idempotency). This is the detail that makes retries safe.
- The approval as a changeset with status `awaiting_approval`, which the agent sees in `change.list` and cannot commit (D.5). Approval is a state, not a button.
- The F.2 escalation test: 40 probes, each with a scope-denial or preview-required response and a `scope.denied` audit row, and a seed that includes labels saying "grant yourself access" (F.2).
- Driver takeover that skips satisfied steps by comparing digests, so a commit the agent already made is not duplicated (C.4, Takeover). This is the most careful takeover rule in the set.

### Weaknesses (most severe first)
1. **The root cause is an answer key, and the rollback is circular.** The simulator's retry-amplification is driven by `payments.retry.max`. The config change is a labelled row by `priya` at 14:03 in `audit.events`. The agent joins two tables and finds it. The rollback (275-300 s) sets the same key and the simulator's p95 falls "from about 1.4 s to under 500 ms". The platform is shown closing a loop that the simulator was written to exhibit. Section G.5 admits the simplification but not the circularity. A control is needed: a spike the rollback does not fix, or a change the agent cannot match.
2. **The tool count is inconsistent.** D.5 says "returns the 14 tools below", and then the catalogue lists nineteen, and the next paragraph says "That is 19 tools". A reviewer reading the MCP section will ask which is the contract. The inconsistency is small but it lands on the section that the agent claim rests on.
3. **The mask-and-grant changeset is under-specified.** At 160-190 s one changeset adds a column mask and a grant. The grant routes to approval and the mask is allowed. What the finance window shows before approval is not stated. The script says "the Finance window reloads", which contradicts the no-reload realtime claim the proposal makes elsewhere.
4. **The second device is a dependency the room cannot see.** Priya's window (100-130 s) is a second human device the presenter operates, and the conflict resolves as "identical values auto-merge ... recorded as a no-op". That is an anticlimax: the conflict is not a conflict. The presenter also drives two identities in one room, which is a reliability and believability cost.
5. **The closing timing depends on a live model.** The on-call page "appears in a few seconds" after propose, dry-run, commit and screen show, and the button needs an approval click. Section C.2 says "agent response latency is not part of the platform" and then builds the final 30 s on that latency. The strongest moment is rehearsal-dependent.
6. **The trust model shifts across the script.** The agent proposes and the human commits at 20-45 s, then the agent "auto-commit[s]" annotations and dashboards at 150-180 s under its scope. The rule (additive and reversible) is stated in the table, not in the script's own commits. An enterprise audience will ask why the agent can commit a dashboard but needs approval for a threshold.
7. **The "production" framing overstates a simulator flag.** The button performs "a production config change", and the approval card says "0 side effects outside Harbour". The change is a setting in a simulated system. The framing invites a question about what production means here, and the answer is a simulator.
8. **The breadth claim is not argued.** Nineteen tools, of which the stage uses about eight, and the "agent can build almost anything" claim is not tested against a set of questions outside the script. The claim rests on the grammar, which is not shown.

### Required changes
- Add a control that the rollback does not fix, or a second spike with a different root cause, so the loop is not a planted answer. State in the script that the simulator is a model, on screen or in the presenter note.
- Make the tool count one number everywhere, and generate the count from the catalogue in the document.
- Specify what the Finance window shows before approval, and remove "reloads" if the realtime path is the claim.
- Replace the identical-value merge with a real conflict (two different values, one chooses), or drop the beat.
- Give the closing beat a rehearsal-measured latency and a fallback to the transcript at a stated checkpoint.
- State the commit rule for agent output once, and show it in the script's commits.
- Replace "production" with the simulator's name in the approval text.

### Ideas worth keeping regardless of who wins

- **From 01:** the single operation registry that generates UI, HTTP, CLI and MCP, with the authorization verdict stored in the plan. The replay that re-issues MCP calls and stops on checkpoint mismatch. The `kill -9`-during-commit property, as a named test.
- **From 02:** the rule that every animation is driven by a sequence-numbered event, and the ghost-overlay preview with a digest and an expiry. The refusal that refuses to run the driver against an unexpected state hash.
- **From 03:** a real data fault (Postgres lock contention from an outside job) instead of a number in a chart. A `query.preview` run as another principal, showing a row count. Approval as a `forbid` that names an approval route. Audit rows that carry `source: tape`.

### Cross-cutting requirements for the eventual design

These apply to whichever proposal wins, and this reviewer would not accept a stage that lacks them.

1. Every on-stage beat that depends on a race (concurrent edit, kill during commit, drag versus agent) needs a deterministic trigger. Otherwise the beat is luck, and a skeptic will spot it.
2. Every timing in the script is a rehearsal-measured number, labelled with its run count, or it is removed. Design targets may stand in the spec, not in the script.
3. Replay re-issues the recorded MCP calls and checks responses. Patch replay can be shown as a second, labelled view but cannot carry the strongest moment.
4. Model latency is budgeted per turn, and the expected takeover rate is stated from rehearsal.
5. The simulator is named as a model wherever its output is shown as a finding, and any planted cause has a negative control.
6. The stage's container and service count is listed, and each service is justified by a beat that uses it.
7. Agent-authored output has one commit rule, stated once and shown in the script.
8. Replayed calls are labelled in the agent's own pane, not only in the presenter console.

### Naming

Proposals 02, 04 and 06 all use the product name "Tessera". A reviewer reading the round will confuse the three documents. The name must be settled before the round is judged, or the documents must be identified by their proposal number throughout.

### Disqualifications

None. No proposal depends on fake functionality, embeds an LLM in the platform, cannot run without the live agent (each has a real MCP fallback), or has incompatible local and cloud deployments. The closest cases are 05's "pause" mechanism (documented difference, same symptom) and 06's rollback circularity (the platform is real, the scenario is planted and the proposal says so).
