# Mission brief, version 2

Version 1 (a domain application with a dashboard) is archived in `_superseded/v1-quayside/`. It
produced a credible design, but that design was not what was wanted. This brief replaces it.

## The product

An **enterprise-grade, composable dashboard and operations platform** that is **built live, on
screen, in real time** during a five-minute demonstration. The platform runs on AWS and also runs
locally in containers, from the same application images.

The platform has an **MCP (Model Context Protocol) server as a first-class interface**, on equal
footing with the web UI and the HTTP API. Through MCP, an AI agent can:

- **act on the platform**: create and arrange panels, dashboards, data sources, queries, alerts,
  workflows, permissions and so on, and see each change appear immediately on every connected
  screen;
- **interrogate the system**: answer questions about any part of the data or of the platform itself
  (for example "why did order latency spike at 14:05?", "who can see the finance board?", "what
  changed in the last hour?") by calling the platform's tools;
- **generate the UI that answers the question**: compose the dashboard, drill-down, form or workflow
  that answers the question from the platform's primitives, live, while the audience watches.

The audience should leave believing two things: the platform is a serious enterprise product, and
an agent connected to it can build almost anything in it, because everything in it is made of
composable primitives that the agent can use.

## Composability is the core requirement

Offer **as many powerful, composable capabilities as possible**. This is a deliberate change from
version 1, which preferred few features. It does not license disconnected features. A capability
counts only if it is a **primitive that composes with the others**:

- it is addressable and usable identically through the web UI, the HTTP API and MCP tools;
- its outputs can be the inputs of other primitives (a query feeds a panel, an alert, a workflow, an
  export, a permission rule, another query);
- it shares the platform's common machinery (one schema/type system, one authorization model, one
  change and audit log, one real-time channel, one undo/versioning model).

A long list of features that do not compose scores lower than a smaller set that does. The ideal is
a large capability surface generated by a small, rigorous core. Examples of the kind of breadth that
is welcome, not mandatory: data sources and connectors, a query layer, transforms, visualizations,
layouts, cross-filtering, drill-down, parameters, alerts and thresholds, annotations, workflows and
actions, forms that write back, scheduled reports, versioning, branching and diffing of dashboards,
templates, sharing, row/column-level security, multi-tenancy, audit, lineage, computed metrics,
anomaly detection, embedding, comments, presence and collaborative editing.

## The agent in the demo

- The platform **must not embed or depend on an LLM** for any capability. All intelligence in the
  platform is deterministic code. The agent is an external MCP client, such as Claude in Claude Code
  or Claude Desktop, which the presenter talks to.
- The MCP server must be good enough that a capable general agent, given only the server's tool
  descriptions, can build substantial UI without bespoke prompting. Its tool design (granularity,
  schemas, discoverability, error messages, previews and dry runs, idempotency, undo) is a primary
  design concern, not an afterthought.
- Agent actions go through **the same authorization, validation, audit and real-time machinery as
  human actions**. The agent acts as a principal with scoped permissions. Its changes are attributed,
  reviewable and reversible.
- Because a live model is an external, non-deterministic dependency, the demo needs a
  **deterministic fallback driver**: a recorded sequence of the same MCP tool calls that can be
  replayed against the platform to produce the same on-screen result, if the model is slow, wrong or
  unreachable. The fallback must be the real MCP path, not a canned UI animation. Proposals should
  design the script so that the live agent is the default and a switch to the fallback is invisible
  or one keystroke.
- Humans and the agent must be able to work on the same dashboard at the same time, with live
  presence and conflict handling.

## Audience and bar

The audience is exceptionally technical: engineers, architects and engineering leaders. They will
not be impressed by superficial complexity, mock functionality, fake metrics, canned animations or
"AI magic" that is really a script. They will be impressed by watching a real system be composed
from real primitives, live, with correct behaviour under concurrency, authorization and failure.

## Unchanged requirements from version 1

- A polished, professional web interface; a genuine backend with persistent storage; domain logic
  beyond CRUD; multiple interacting users, roles or sessions; real-time state changes; nontrivial
  workflows with observable state transitions; meaningful security and authorization boundaries;
  realistic, reproducible sample data and a realistic live data feed; automated end-to-end
  validation.
- AWS deployment plus local containers from **the same application images**. The local deployment
  is not a diminished simulation. Cloud integrations sit behind explicit interfaces, and local
  substitutes preserve externally observable behaviour, with the differences documented.
- No paid APIs or unpredictable third-party services in the platform's core. The external agent is
  the single allowed exception, and it is covered by the fallback driver.
- **Five-minute demonstration (about 300 s)**, a choreographed sequence. Each operation builds on the
  previous one, shows meaningful system behaviour, reveals more capability, produces an immediate
  visible result and needs minimal explanation. The first 30 s establish purpose and interest; the
  final 30 s deliver the strongest moment. Avoid setup, waiting, navigating and long explanation.
  Typing a prompt to the agent is allowed, but keep prompts short and visible, and keep agent
  latency inside the choreography.
- Demonstration reliability: one-command local startup; one-command demo reset; predictable initial
  conditions; automated browser-based rehearsal (including the MCP fallback driver); several
  simultaneous browser sessions; stable identities and permissions; health and readiness checks;
  recovery after an interrupted demo; identical core behaviour locally and on AWS. The platform must
  work outside the script.

## Required competitor deliverables

A. Product concept. B. Capability inventory: every primitive, how it composes with the others, and
which are demonstrated versus supporting; include a composition map. C. Five-minute live script:
time, presenter action (including the exact agent prompts), expected behaviour (including the MCP
tool calls the agent is expected to make), visible result, capabilities demonstrated, transition.
D. Technical architecture, including **the MCP server design: the tool catalogue with schemas or
signatures, resources, how the agent discovers capabilities, how it previews and commits changes,
how it is authorized and audited, and how agent-generated UI is represented (a declarative
dashboard and panel specification language, not generated code)**. E. AWS and local deployment.
F. The five strongest technical claims, each with an executable test or observable behaviour.
G. Failure analysis, including agent failure modes: a wrong tool call, hallucinated fields, slow
responses, and the fallback. H. Feasibility.

## Evaluation framework (0–10 per criterion)

| Criterion | Weight |
|---|---:|
| Demonstrable technical depth | 20% |
| Composability and breadth of capability | 20% |
| Agent/MCP integration quality | 15% |
| Visual and interactive impact | 15% |
| Credibility to expert engineers | 10% |
| Five-minute narrative quality | 10% |
| Implementation feasibility | 5% |
| Live-demo reliability | 5% |

Disqualify proposals that depend on fake functionality, embed an LLM in the platform, cannot work
without the live agent, or have fundamentally incompatible local and cloud deployments.

## House rule for every document in this directory

No estimates of how long work will take: no hours, days, weeks, sprints, story points, t-shirt sizes
or "quick". Convey feasibility by what the work touches and by dependency order. Measured or
estimated quantities (latency, throughput, row counts) are fine when labelled.
